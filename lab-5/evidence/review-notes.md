## Порядок действий с RAID5

1. Зафиксировать соответствие d1-d4 файлам образов UTM и идентификаторам Windows. После отключения диска его номер в Windows может измениться
2. Выполнить часть 2: простой NTFS-том 1 ГБ на d1, точка подключения `C:\Volume1`, сведения об устройствах, логических дисках, разделах и томах. Проверить скрипт создания T: на отдельном учебном диске с отказом и согласием пользователя
3. Удалить учебные тома части 2. Для RAID5 перевести d1-d3 в динамические диски Windows и создать W:. Оставить d4 свободным для ремонта
4. Записать несколько небольших файлов на W:, сохранить их контрольные суммы. Дождаться завершения первоначальной синхронизации RAID5
5. Штатно выключить s1. Отсоединить только d3 в UTM, сохранив файл образа. Запустить сервер, проверить чтение файлов и их контрольные суммы, снять состояние RAID5 в Диспетчере дисков
6. В Диспетчере дисков восстановить RAID5 на d4. Дождаться завершения регенерации, снять состояние и повторно проверить файлы. Во время ремонта не подключать d3 обратно
7. Штатно выключить s1, вернуть исходный образ d3. После запуска проверить идентификаторы всех четырех учебных дисков и очистить только их старые тома и разделы
8. Скриптом DiskPart создать V: RAID5 на d1-d4. Системный диск не должен попадать в список дисков скрипта

При одинаковых дисках полезная емкость RAID5 до служебных расходов равна `(N - 1) * емкость одного диска`. Для трех дисков по 4 ГиБ это около 8 ГиБ, для четырех около 12 ГиБ. В отчете указываем фактически полученные размеры и единицы измерения

Динамический образ диска UTM и динамический диск Windows означают разное. Первый экономит место на Mac, второй нужен для программного RAID5 в Диспетчере дисков. Для пула Storage Spaces берем семь новых дисков, а не использованные динамические d1-d4

## iSCSI

s1 выступает iSCSI Target, s2 выступает iSCSI Initiator. Файл виртуального диска LUN1 объемом 5 ГБ должен храниться на V: сервера s1. На s2 подключаем именно этот LUN, создаем NTFS-том и назначаем R:

Проверки: соединение с порталом s1, разрешение инициатора s2 по IP, наличие диска с `BusType = iSCSI`, физические и логические устройства, разделы, тома и чтение записанного тестового файла. Наличие роли Target на s1 не подтверждает подключение на s2

## Storage Spaces и две отказавшие единицы

Пул из семи дисков создаем через Server Manager, как требует часть 5, п.2. Перед выбором устройств проверяем емкость, идентификаторы и `CanPool`. Не выбираем системный диск, d1-d4 и iSCSI LUN

Для зеркала используем `ResiliencySettingName = Mirror`, две копии данных и максимальный размер. Сохраняем полученные `Size`, `FootprintOnPool`, `NumberOfColumns`, `NumberOfDataCopies` и `PhysicalDiskRedundancy`, затем удаляем этот виртуальный диск перед созданием Parity

Для устойчивости к двум отказам недостаточно указать только `Parity`: по умолчанию создается одинарная четность. Нужны `PhysicalDiskRedundancy = 2` и `ProvisioningType = Fixed`. Семь дисков соответствуют минимальному числу для двойной четности. Проверяем фактическую геометрию и заявленную избыточность созданного объекта. Основание: [New-VirtualDisk](https://learn.microsoft.com/en-us/powershell/module/storage/new-virtualdisk), [Set-ResiliencySetting](https://learn.microsoft.com/en-us/powershell/module/storage/set-resiliencysetting?view=windowsserver2022-ps)

Для семи дисков по 10 ГиБ теоретический верхний предел зеркала с двумя копиями равен 35 ГиБ. При двойной четности и семи колонках расчетный предел равен 50 ГиБ. Служебные данные, резерв под журнал и геометрия размещения уменьшают доступный размер. Эти оценки не записываем в отчет как измеренный результат. Для сравнения используем фактическое свойство `Size`, полученное после создания каждого виртуального диска

Не заменяем двойную четность одинарной, не уменьшаем число дисков и не используем Thin ради обхода ошибки. При отказе создания проверяем свободную емкость пула и поддерживаемые настройки избыточности
