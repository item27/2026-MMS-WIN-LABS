# Лабораторная работа №5

## Задание и выбранная среда

- Работаем только над лабораторной №5 v.2 по документу `sources/awin-5-2025.docx`. Дословный текст находится в `lab-5-task.md`
- Чужой `Lab-4.docx` относится к другой работе и не является решением пятой лабораторной
- Ветка текущей попытки: `lab-5-attempt-1`. Соблюдай формат репозитория `lab-x-attempt-y`
- Пользователь выбрал UTM и Windows Server 2022 x64. Не меняй архитектуру или гипервизор без обсуждения
- Пользователь запросил по 2 ядра на каждую ВМ. Для x86_64 на M5 требуется Force Multicore. Меняй число ядер только на штатно выключенной ВМ и проверяй значение через configuration UTM
- Имена Windows: `ad-srv` и `ad-srv-2`. Домен: `GMAKMA.local`, NetBIOS: `GMAKMA`. Перед использованием проверь фактические значения в гостевых ОС
- План сети: один изолированный LAN, `ad-srv` = `10.0.0.1/8`, `ad-srv-2` = `10.0.0.2/8`, DNS обоих серверов = `10.0.0.1`. DHCP для этой работы не разворачиваем

## Выполнение

- До действий читай `evidence/session-status.md` и проверяй реальные ВМ. Состояние из текста или старого скриншота не заменяет проверку
- Для работы используем два сервера. Отдельный клиент из лабораторной №4 не нужен
- Пользователь прямо разрешил штатную автоматизацию UTM через AppleScript. Термины проверяй в `/Applications/UTM.app/Contents/Resources/UTM.sdef`, состояние ВМ проверяй до изменений
- Для снимков гостевой Windows доступна команда UTM `capture screen`, сохраняющая исходный PNG без рамки Mac
- Перед оценкой экрана выводи нужную консоль ВМ на передний план через UTM Window menu и проверяй свежий кадр. При фоновой консоли capture screen может вернуть старое изображение, даже когда Windows уже перезагружается. Сверяй состояние с гостевым агентом, не делай вывод о зависании по старому кадру
- Оригинальный ISO UTM Guest Tools содержит `Autounattend.xml` с отключением UAC. Не подключай его до установки Windows. Подготовлен `utm-guest-tools-manual.iso` только с неизменённым официальным EXE и файлом лицензии
- Сохрани исходные снимки готового доменного стенда до подключения учебных дисков
- На `ad-srv` добавляем четыре отдельных диска d1-d4 по 4 ГиБ. Семь дисков по 10 ГиБ добавляем только перед Storage Spaces
- Перед любым изменением разделов связывай имя файла образа UTM, идентификатор накопителя и номер диска Windows. Номера могут измениться после отключения d3
- Системные, загрузочные и неизвестные диски не форматируем. Команды с фиксированным номером диска допустимы только после сверки в текущей ВМ
- Перед опытом с отказом d3 копируем qcow2 за пределы `.utm` и сохраняем исходную Drive-запись и её позицию. В UTM 5.0.9 исключение диска из `drives` через update configuration удаляет неупомянутый образ из Data
- Для отключения предпочтительно сохранить запись d3 и временно задать interface=none, затем вернуть прежний интерфейс. Этот способ проверяем на стенде по исчезновению устройства из Windows и деградации RAID. До этой проверки не объявляем опыт выполненным
- Обычный API-add после удаления записи не восстанавливает прежний Identifier. Для возврата удалённой записи нужны исходные config.plist/образ и reload configuration на остановленной ВМ
- Не вычисляй Windows SerialNumber из UTM Identifier без фактической сверки. Для SCSI UTM не передаёт serial, для VirtIO передаёт. Сначала проверяем гостевой драйвер и реальные идентификаторы
- В RAID5 используем динамические диски Windows. Для Storage Spaces нужны отдельные базовые диски, доступные для пула
- Проверку iSCSI подтверждаем на `ad-srv-2` по BusType, подключённой сессии и файлу на R:. Одного существования LUN на сервере недостаточно
- GUI-действия, явно указанные в ТЗ, выполняем в Disk Management и Server Manager
