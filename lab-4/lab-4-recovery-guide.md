# Лабораторная 4: восстановление удалённой связи Failover

Сценарий для защиты на существующем стенде: удалить связь через DHCP, восстановить её скриптом и проверить свежую аренду на клиенте. Проверка выполнена 18 ноября 2026 года. Связь восстановилась скриптом, для возобновления выдачи адресов потребовался отдельный перезапуск службы DHCP на основном сервере

## Что подготовлено

- VM104, win-labs-1: AD-SRV.GMAKMA.local, основной DHCP 10.0.0.1
- VM109, win-labe-3: AD-SRV-2.GMAKMA.local, резервный DHCP 10.0.0.2
- VM105, win-labs-2: AD-CLIENT, клиент Windows 10

На VM104 в C:\Lab4 сохранены lab4-repair-failover.ps1 и repair-parameters.json. Запускать скрипт локально на VM104 в PowerShell от имени администратора. Исходник в репозитории: [lab4-repair-failover.ps1](scripts/lab4-repair-failover.ps1)

Скрипт восстанавливает отсутствующую на обоих серверах связь Lab4 для области 10.0.0.0. Исходная область должна оставаться активной на основном сервере, на резервном её быть не должно. При конфликте настроек или односторонней связи скрипт останавливается без автоматической перезаписи

## 1. Показать исходное состояние

На VM104 открыть Server Manager -> Tools -> DHCP -> ad-srv.gmakma.local -> IPv4 -> Scope [10.0.0.0] Lab2Scope -> Properties -> Failover

Показать Lab4, Hot standby, роль Active, резерв 35%, MCLT 30 минут, интервал перехода 1 минута и оба состояния Normal. На VM109 та же область должна показывать роль Standby и Normal/Normal

До удаления проверить запуск на здоровой конфигурации

```powershell
C:/Lab4/lab4-repair-failover.ps1 -ConfigPath C:/Lab4/repair-parameters.json -Apply
```

Ожидается UNCHANGED. Это означает, что проверяемые параметры совпадают и оба сервера показывают Normal. Свежую выдачу адреса эта проверка не подтверждает

## 2. Удалить связь через UI

1. На VM104 нажать правой кнопкой по области Lab2Scope -> Deconfigure Failover
2. Проверить предупреждение: область будет удалена с резервного сервера. Подтвердить и дождаться успешного завершения
3. Нажать правой кнопкой по IPv4 -> Properties -> Failover
4. Если осталась пустая связь Lab4, выделить её -> Delete. В подтверждении проверить, что список Scopes пустой. Дождаться успешного завершения
5. Показать пустой список Failover. На VM109 обновить IPv4 и проверить отсутствие области 10.0.0.0. Исходную область Lab2Scope на VM104 сохранить

Область на основном сервере вручную не удалять: из неё скрипт восстановит конфигурацию партнёра. Перед этим демо на VM104 создана резервная копия DHCP в C:\Lab4\before-demo

## 3. Восстановить связь

В PowerShell VM104 выполнить ту же команду

```powershell
C:/Lab4/lab4-repair-failover.ps1 -ConfigPath C:/Lab4/repair-parameters.json -Apply
```

Перед созданием связи скрипт сохраняет копию базы основного DHCP в отдельном каталоге C:\bak-dhcp\before-failover-repair-*. При запросе Enter lab failover shared secret ввести общий секрет из задания awin_4_2025.docx и нажать Enter

Ожидается RESTORED. Закрыть и заново открыть Properties -> Failover на обоих серверах: проверить Normal/Normal, роли Active и Standby и параметры из первого шага. На VM109 должна снова появиться область 10.0.0.0

Повторить запуск скрипта: ожидается UNCHANGED без запроса секрета

## 4. Проверить свежую аренду

На VM105 открыть командную строку от имени администратора. Команды выполнять по одной и дожидаться завершения каждой

```text
ipconfig /release
```

Освобождает текущую аренду. Выданный IPv4 и шлюз временно исчезают

```text
ipconfig /renew
```

Запрашивает адрес у DHCP. Таймаут означает, что проверка выдачи не пройдена, даже если в Failover показано Normal

```text
ipconfig /all
```

Показать DHCP Enabled: Yes, адрес из области, обновлённое Lease Obtained, DHCP Server, шлюз и DNS. В конце нашей проверки клиент получил 10.0.0.100 от 10.0.0.1, шлюз 10.0.0.1 и DNS 10.0.0.2. MAC остался BC-24-11-53-4F-29

Сказать: "Связь восстановлена на обоих серверах. Клиент освободил старую аренду и получил новую от основного DHCP"

## Если Normal есть, а renew завершается таймаутом

В нашем демо сначала возник именно этот сбой. На основном сервере область была активна, оставались 93 свободных адреса, авторизация в домене и привязка DHCP к Ethernet были включены, MAC-фильтры выключены. Захват Packet Monitor показал запросы клиента на UDP 67 и потери в TCP/IP с причиной Port unreachable

Перезапуск адаптера клиента через ncpa.cpl -> Ethernet -> Disable, затем Enable не помог. После перезапуска службы DHCP на VM104 выдача заработала

```powershell
Restart-Service DHCPServer
```

Команда выполняется на VM104 в PowerShell от имени администратора. Дождаться завершения. На обоих серверах заново открыть свойства области -> Failover и проверить Normal/Normal, затем на клиенте снова выполнить release, renew и all. Скрипт восстановления сам службу не перезапускает

Во время перезапуска клиент получил 10.0.0.162 от резервного DHCP 10.0.0.2. При следующем release/renew с обоими работающими серверами получен 10.0.0.100 от основного DHCP 10.0.0.1. Финальная проверка скриптом снова вернула UNCHANGED и Normal на обоих серверах

Точная причина первоначального сбоя приёма запросов не установлена. Перезапуск службы помог в этой проверке, но применять его как универсальное исправление любого таймаута нельзя. Трасса сохранена на VM104 в C:\Lab4\dhcp.etl и C:\Lab4\dhcp.txt. Захват остановлен, временный фильтр Packet Monitor удалён

## Что означает результат

Проверены восстановление удалённой связи, появление области на резерве, повторный запуск без изменений и свежая выдача аренды после дополнительного перезапуска службы. Самостоятельное восстановление выдачи одним скриптом в этом прогоне не подтверждено

Normal описывает состояние связи партнёров. Проверка release/renew нужна отдельно: она показывает, что клиент действительно получает адрес. MCLT ограничивает продление аренды одним партнёром без согласования с другим. Общий секрет используется для проверки сообщений между DHCP-партнёрами

Этот сценарий дополняет [основную памятку по UI](lab-4-guide.md). Остальные требования лабораторной и все возможные повреждения конфигурации этим прогоном не проверялись
