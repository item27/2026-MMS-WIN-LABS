# Лабораторная 4: показ DHCP через UI

Памятка для показа DHCP на существующем стенде. Резервирование, политика по MAC и работа резервного сервера проверены через UI в записях от 18 ноября 2026 года

## 1. Подготовка записи

Включить VM104, VM105 и VM109. На клиенте заранее войти под существующим администратором домена, чтобы менять свойства адаптера. Пароль в памятку и видео не включать

- win-labs-1, VM104: AD-SRV, основной DHCP, 10.0.0.1
- win-labs-2, VM105: AD-CLIENT, клиент Windows 10
- win-labe-3, VM109: AD-SRV-2, резервный DHCP, контроллер домена и DNS, 10.0.0.2

Записывать окно VNC или область, в которой видна одна выбранная ВМ. Перед переключением проверить, что новое окно попадает в запись. Оставлять результат на экране на несколько секунд

## 2. Что показать на основном DHCP

На VM104 открыть Server Manager -> Tools -> DHCP. В дереве раскрыть ad-srv.gmakma.local -> IPv4 -> Scope [10.0.0.0] Lab2Scope

1. Правой кнопкой по области -> Properties -> General: диапазон 10.0.0.100-10.0.0.200, маска 255.0.0.0, аренда 1 час
2. На вкладке Failover: отношение Lab4, партнёр AD-SRV-2, режим Hot standby, основной сервер Active, состояния обоих серверов Normal, резерв 35%, MCLT 30 минут, интервал перехода 1 минута
3. В Address Pool: исключение 10.0.0.195-10.0.0.200
4. В Reservations: адрес 10.0.0.199. Соответствие MAC 00-01-02-03-04-05 проверить фактической выдачей на клиенте
5. В Scope Options: Router 10.0.0.1, DNS 10.0.0.2, суффикс GMAKMA.local
6. В Policies: Lab4Mac включена. Правой кнопкой по политике -> Properties -> Conditions: MAC Address Equals AA0102*. На вкладке Options выбрать строку 003 Router и показать 10.10.10.10
7. В Address Leases показать аренды. Для статистики нажать правой кнопкой по области -> Display Statistics

Сказать: "Основной DHCP выдаёт адреса из области. Для одного MAC есть резервирование, для другого действует политика со своим шлюзом. Второй сервер настроен как резервный"

## 3. Исходное состояние клиента

На VM105 открыть командную строку или PowerShell с правами администратора. Выполнить одну команду

```text
ipconfig /all
```

Показать Physical Address, DHCP Enabled, IPv4 Address, Default Gateway, DHCP Server и DNS Servers. Перед новой проверкой записать фактический MAC. На исходной записи видны BC-24-11-53-4F-29, IP 10.0.0.100, DHCP 10.0.0.1, шлюз 10.0.0.1 и DNS 10.0.0.2

## 4. Резервирование и смена MAC

Открыть Device Manager через меню Пуск или Win+R -> devmgmt.msc. Раскрыть Network adapters -> Intel(R) PRO/1000 MT Network Connection. Правой кнопкой -> Properties -> Advanced -> Locally Administered Address

При выбранном Not Present собственное значение MAC не задано. Для теста выбрать Value, ввести 000102030405 без дефисов и нажать OK. Дождаться завершения перезапуска адаптера

В терминале выполнить команды по одной, после каждой показать результат

```text
ipconfig /release
```

Освобождает текущую аренду IPv4. До следующего запроса клиент временно остаётся без выданного DHCP адреса

```text
ipconfig /renew
```

Запрашивает аренду у DHCP. Дождаться завершения команды

```text
ipconfig /all
```

Проверить MAC 00-01-02-03-04-05 и адрес 10.0.0.199. При доступном основном сервере ожидается DHCP Server 10.0.0.1. Если MAC остался прежним, сначала проверить применение свойства адаптера

Сказать: "Адрес .199 получен автоматически и совпадает с резервированием на сервере"

## 5. Политика по MAC

В том же свойстве адаптера заменить значение на AA0102030405 и нажать OK. Снова выполнить release, затем renew, затем all отдельными командами

Проверить Physical Address AA-01-02-03-04-05 и Default Gateway 10.10.10.10. Динамический IP может отличаться от .100, его точное значение не доказывает срабатывание политики. Здесь проверяем именно выданный шлюз

Сказать: "Префикс MAC совпал с условием Lab4Mac, поэтому DHCP выдал шлюз 10.10.10.10"

Вернуться в Locally Administered Address, выбрать Not Present и нажать OK. Повторить release, renew и all. Проверить исходный MAC и шлюз 10.0.0.1 до теста отказа

## 6. Проверка резервного сервера

До отключения сети на VM109 открыть Server Manager -> Tools -> DHCP -> IPv4 -> область -> Properties -> Failover. Проверить роль Standby и исходное состояние Normal. На клиенте показать текущий DHCP Server

1. На VM104 открыть Win+R -> ncpa.cpl -> правой кнопкой по Ethernet -> Disable. Дождаться надписи Disabled. Это имитация отказа сети основного DHCP, консоль VNC остаётся доступной через гипервизор
2. На VM109 закрыть свойства области и открыть их снова -> Failover. В проверке резерв перешёл в Partner down, для партнёра показано Not available. Если окно было открыто до отказа, оно может показывать прежнее состояние
3. На VM105 выполнить ipconfig /release, затем ipconfig /renew, затем ipconfig /all по одной. Дождаться завершения renew. В записи клиент получил 10.0.0.100 от DHCP Server 10.0.0.2, время Lease Obtained обновилось
4. Если на защите просят перезапустить адаптер клиента, открыть на VM105 ncpa.cpl -> Ethernet -> Disable, затем Enable. После подключения выполнить те же команды и проверить DHCP Server
5. На VM104 открыть меню Ethernet -> Enable. Дождаться подключения к GMAKMA.local
6. На VM109 снова открыть Properties -> Failover. В конце проверки State of this Server и State of Partner Server вернулись в Normal. MAC клиента к этому моменту восстановлен в BC-24-11-53-4F-29

Если нужно имитировать именно отключение кабеля, альтернативный путь: Proxmox -> VM104 -> Hardware -> сетевой адаптер -> Edit -> Disconnect, если флажок доступен. После теста снять Disconnect. В нашей записи использовано отключение Ethernet внутри Windows

Если renew не завершается успешно, не объявлять проверку пройденной. Сначала восстановить сеть основного сервера, затем разобрать результат

## 7. Как объяснить статусы и команды

Normal означает нормальную связь партнёров. Communication interrupted означает потерю связи, но само по себе не доказывает остановку партнёра. Partner down - отдельное состояние. Не называть его проверенным, если на экране показан только разрыв связи

Интервал 1 минута относится к настроенному автоматическому переходу после потери связи. Он не означает, что весь пул немедленно переходит резервному серверу. После Partner down для полного принятия пула учитывается MCLT

Резерв 35% позволяет резервному серверу обслуживать новых клиентов из своей части свободных адресов. Успешную выдачу проверяем на клиенте по строке DHCP Server

Release освобождает аренду, renew запрашивает её, all показывает подробные параметры. Flushdns очищает DNS-кэш и для этой проверки аренды не нужен

## 8. Подтверждённые результаты

В итоговом видео lab4-demo-tight-1.5x.mp4 длительностью 3 минуты 2 секунды:

- 00:00 - настройки основного DHCP
- 01:10 - смена MAC и резервирование .199
- 01:32 - проверка политики по MAC
- 01:55 - возврат исходного MAC
- 02:17 - резервный сервер и отключение основного
- 02:33 - запрос аренды при отказе, с 02:45 виден DHCP Server 10.0.0.2
- 02:48 - Partner down, затем включение сети основного
- 02:59 - возврат обоих состояний в Normal

- MAC 00-01-02-03-04-05: автоматически получен адрес 10.0.0.199 от DHCP 10.0.0.1
- MAC AA-01-02-03-04-05: получен адрес 10.0.0.102 и шлюз политики 10.10.10.10
- После Not Present: восстановлен MAC BC-24-11-53-4F-29, получены адрес 10.0.0.100 и шлюз 10.0.0.1
- При отключённом Ethernet VM104: клиент получил свежую аренду от DHCP 10.0.0.2, резерв показал Partner down
- После Enable на VM104: оба состояния Failover вернулись в Normal

В проверках смены MAC выдавались аренды на 30 минут. При отключённом основном сервере аренда от резерва была на 1 час. В General области настроен 1 час, при failover фактический срок отдельной аренды может отличаться

Этот показ не закрывает все требования отчёта. В текущем отчёте отдельно отмечены включённый IPv6 и отличия ролей серверов от задания. DNS .2 соответствует фактическому контроллеру домена на нашем стенде
